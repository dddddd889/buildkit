第五题：诊断一份“缓存成功”报告

3 分钟阅读 · 五题自测复盘：层缓存、下载缓存和 builder

题目

每次 CI 创建新 builder，并配置 registry cache 的 --cache-from 和 --cache-to mode=max，推送最终应用镜像。Dockerfile：

FROM node:24 AS build
WORKDIR /app
COPY package.json yarn.lock ./
RUN --mount=type=cache,target=/yarn-cache \
    yarn install --frozen-lockfile --prefer-offline
COPY . .
RUN yarn build
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html

同事说：“安装显示 CACHED，证明 /yarn-cache 已上传，改 lock 也只下载新增包。缓存文件在最终 Nginx 容器里，线上重启也能利用它。”

  1. 逐条指出错误，以及 CACHED 实际证明什么。
  2. 找出 Dockerfile 下载缓存配置自身的问题。
  3. 应用镜像、远端层缓存、下载缓存分别在哪里，由谁使用？
  4. 安装耗时 60 秒时，如何区分层缓存未命中、重复下载、解压或编译慢？

我的回答（原文）

  1. yarn-cache不会上传；你需要能访问到下载缓存目录yarn-cache才能改lock只增量包更新；缓存文件是指下载缓存的话不会进最终镜像。只能证明：当前机器下命中了buildkit下载缓存。
  2. yarn并不会认这个目录。
  3. 应用镜像只有最后一个nginx生效，由下游dockerfile使用；远端层缓存跟着镜像一起，pull和build都会拉下来，下载缓存挂载只在宿主本地，只给当前宿主机下次build使用。
  4. 查下本地的下载缓存挂载是否仍有效，是否会饿缓存重新编译。

知识盲点与修正

第 1 点前半正确，最后一句是核心错误：CACHED 表示安装命令没有执行，证明复用了步骤结果，不能证明读取过下载缓存。恢复下载包后仍需生成 node_modules，不是自动增量修改旧 node_modules。

第 2 点正确：题目没有配置 Yarn 使用 /yarn-cache，单独挂载目录无效。应设 YARN_CACHE_FOLDER=/yarn-cache，或安装时指定 --cache-folder /yarn-cache。

第 3 点需要重新分开：

内容 本题中的位置 使用者
应用镜像 app:提交SHA；最终 Nginx 文件系统及静态文件 Docker/Kubernetes 拉取并运行，也可被后续 Dockerfile 继承
registry 层缓存 独立的 app:buildcache 引用，包含 mode=max 导出的中间构建结果 BuildKit 通过 --cache-from 导入
下载挂载 具体 BuildKit 存储内的独立目录 Yarn/npm 在安装实际执行时读取、写入

本题不是 inline cache，不能说层缓存一定随应用镜像一起。普通 docker pull 应用镜像不会自动导入独立的 registry cache。即使用 inline，拉到 Docker 本地也不等于另一套 BuildKit 已自动导入。

多阶段最终镜像以最后阶段为基础，但 COPY --from 引入的产物同样存在；被丢弃阶段的依赖和缓存不会因此自动进入最终镜像。线上容器重启与构建缓存无关。

第 4 点缺少可执行的诊断路径。按下面顺序取证：

  1. 看安装步骤是 CACHED 还是有真正的安装日志。若为 CACHED，命令未执行；其他下载、导出耗时应另算。
  2. 安装重跑时，检查远端导入是否成功，比较平台、基础镜像、命令及依赖输入，定位层缓存不匹配原因。
  3. 确认 Yarn 的实际缓存路径、挂载是否为同一存储、缓存包是否存在，结合请求日志判断是否重新下载。
  4. 下载很少仍耗时，观察链接、解压、postinstall、原生编译等阶段；还要区分命令执行与 BuildKit 保存结果、导出镜像的耗时。
  5. 必要时用全新实验编号让安装真正执行，再做受控离线验证；安装显示 CACHED 的离线测试不能证明下载缓存可用。
