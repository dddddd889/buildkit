逐条修正

3 分钟阅读 · 我的七点总结与修正：用白话重新理解缓存

本课内容第 1 点：默认选最后阶段，但可以指定其他阶段第 2 点：远端缓存不只是旧文件，还需要对应记录第 3 点：下载缓存跟着 BuildKit 的存储，不跟着当前终端第 4 点：需要搬运时，是构建前恢复、构建后保存第 5 点：看到 CACHED，说明安装根本没运行第 6 点：不要用“外置、内置”区分这两种缓存第 7 点：挂载内容变了，不会单独触发 RUN 重跑

第 1 点：默认选最后阶段，但可以指定其他阶段

多阶段 Dockerfile 默认以最后一个阶段作为构建目标。使用 --target build 时，也能把前面的 build 阶段作为目标。

最后阶段可以通过 COPY --from=build 拿到其他阶段的产物，因此不是“前面阶段做的东西全部丢掉”，而是只有主动复制过来的文件才会进入这个最终阶段。最后阶段也不一定是可运行的应用镜像，例如本教程的 scratch 阶段用于导出静态文件。

第 2 点：远端缓存不只是旧文件，还需要对应记录

基本正确，但不能理解成“远端看到旧文件就直接套用”。BuildKit 还需要知道：哪些输入和命令，对应哪份构建结果。

白话说，旧文件是做好的结果，缓存记录是帮助找到正确结果的说明书。输入匹配时可以整步复用；输入变化时，应重新找匹配结果或实际执行。

第 3 点：下载缓存跟着 BuildKit 的存储，不跟着当前终端

方向正确。准确位置由 BuildKit 配置决定，可能在 Docker volume、挂载磁盘，或者远程构建机器上。

本地终端发送构建命令，不代表缓存就存到当前项目目录。两个 Runner 连接同一个远程 BuildKit，可能共享存储；同一台 Runner 新建两套独立 builder，通常不会自动共享缓存。

第 4 点：需要搬运时，是构建前恢复、构建后保存

如果一直使用同一套 BuildKit 存储，且下载缓存没有被清理，不需要每次额外导出、恢复。

如果换成独立 builder，又想少下载包，流程应是：

构建前：恢复之前保存的下载包，让安装步骤能够读取。
安装时：读取旧包，补下载缺少的包，重新生成 node_modules。
构建后：保存更新后的下载包，供下次恢复。

这里“增量”指尽量少下载，不代表拿旧 node_modules 自动增量修改。普通 --cache-to 不会替你导出 cache mount 的下载目录，目录搬运需要另外实现。

第 5 点：看到 CACHED，说明安装根本没运行

安装步骤显示 CACHED，说明直接复用了步骤结果，不能证明下载缓存被读取。

要验证下载缓存，先让安装真正重跑。可以改实验参数，不必为了实验修改 package.json；如果改依赖清单，也要保持锁文件一致，否则安装失败可能只是清单不匹配。

更明确的验证：先填满所需下载包，再用新实验编号让安装真正执行，禁用执行步骤网络并使用包管理器的离线模式。如果仍安装成功，才证明已有下载包足够。安装脚本可能另外联网，因此应选受控实验，不承诺所有项目都能离线安装。

CACHED：这一步没做，直接拿上次结果。
下载缓存复用：这一步做了，但包尽量从已有目录里拿。

第 6 点：不要用“外置、内置”区分这两种缓存

“下载缓存外置，远端层缓存内置”容易越说越乱。换成下面两个问题：

问什么 层缓存 下载缓存挂载
保存什么？ 一步已经做好的文件系统结果，例如 node_modules 重新安装时可复用的下载包
命中后还执行安装吗？ 整个安装步骤跳过 安装仍执行，只是尽量少下载

再单独问“存在哪里”：层缓存可以留在 builder 内部，也可以导出到文件目录或镜像仓库；下载缓存挂载默认留在具体 BuildKit 存储里。

inline 说的是“缓存说明书附在哪里”，不是另一种下载目录。

第 7 点：挂载内容变了，不会单独触发 RUN 重跑

这一点正确，但跨应用复用还需要条件。

/cache 文件变化
  → 不会只因这个变化就强制 RUN 重跑。

RUN 已经 CACHED
  → 命令没有执行。
  → 不会读取 /cache 中刚变化的内容。

不同应用镜像可以在兼容的配置下使用同一套 BuildKit 存储和相同 cache id。是否共享不由最终镜像名字决定；还要考虑缓存存储、标识、访问权限、并发模式及包管理器格式是否兼容。相同 id 在独立存储里不是同一份目录。
